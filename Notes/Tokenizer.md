# Tokenizer（分词器）
## 一、定义
Tokenizer 负责把文本转换成模型可处理的 token ID，也能把 token ID 还原成文本。

例如，用户输入：I love machine learning.

Tokenizer 可能将其处理为：
```text
拆分结果：["I", " love", " machine", " learning", "."]
数字编号：[40, 1842, 7621, 5913, 13]
```

需要理解三个概念：

- **Token**：文本切分后的基本单位，可以是一个字、一个单词、词的一部分或者标点符号。
- **Vocabulary（词表）**：存储 Token 与 Token ID 对应关系的集合。
- **Token ID**：Token 对应的整数编号，供神经网络使用。

**注意：Tokenizer 本身不负责理解文本含义，只负责文本的切分与编码。空格也可能和后面的单词组成同一个 token，因为格式本身也是文本信息。**
## 二、 分词方式
常见分词方式：
| 分词方式 | 示例 | 好处 | 问题 |
|:---:|:---:|:---:|:---:|
| 字符切分 | `c` `a` `t` | 单位较小，容易组合出新词 |序列太长|
| 单词切分 | `cat` `playing` | 常用词可用一个单位表示 | 词表庞大，生僻字难处理|
| 子词切分 | `play` `ing` | 常见片段用大单位，少见内容拆小 | 切分规则未必合理 |
| 字节切分 | `41` `E4B8AD` | 可以覆盖任意文本的底层编码 | 序列更长，一个字符可能需要多个单位 |

很多 LLM 使用子词或与字节结合的切分方式。核心思路是：
>常见内容尽量合起来，少见内容允许拆开。

比如，一个不常见的英文长词，可以由几个熟悉的片段组成，而不必为每个长词都准备独立编号。

## 三、BPE 算法

BPE（Byte Pair Encoding）是 LLM 中广泛使用的一类分词算法。可以理解为“反复合并常见片段”。

核心思想：**从最小单位开始，不断将出现频率最高的相邻单位合并，逐渐得到更大的 Token 。**

### 1、初始化
假设训练语料只有三个单词：
```text
low
lower
lowest
```
最初将每个单词拆成字符：
```text
l o w
l o w e r
l o w e s t
```
### 2、统计相邻字符对频率
| 字符对 | 出现次数 |
|:---:|:---:|
|`l o`|3|
|`o w`|3|
|`w e`|2|
|`e r`|1|
|`e s`|1|
|`s t`|1|

假设第一次选择`l o`进行合并：
```text
lo w
lo w e r
lo w e s t
```
### 3、继续合并
重新统计相邻 Tkoen 对，`lo w`出现 3 次，为最高频组合，因此第二次合并：
```text
low
low e r
low e s t
```
第三次将`low e`合并为`lowe`：
```text
low
lowe r
lowe s t
```
以此往后统计合并出`lower`、`lowes`、`lowest`。
## 4、BPE 的停止条件与使用
BPE 会不断合并相邻 Token，直到达到指定的词表规模，或者满足其他停止条件（例如没有可合并的相邻 Token 对）。最终形成：

- Vocabulary：词表。
- Merge Rules：合并规则及其优先级。

### 4.1、这个例子最终得到的词表

假设每个单词出现一次，只在单词内部合并，不加入特殊 Token，并按照前文的顺序一直合并到三个单词都成为完整 Token。

初始词表包含 7 个字符，每次合并再加入一个新 Token，因此最终词表包含 **13 个 Token**：

```text
初始 Token：l、o、w、e、r、s、t
新增 Token：lo、low、lowe、lower、lowes、lowest
```

**合并不会删除词表中的旧 Token。** 例如，生成 `low` 后，`l`、`o`、`w` 和 `lo` 仍然保留，以便处理其他输入。

可以为它们分配如下 ID（仅为示意，具体编号由实现决定）：

| Token | Token ID | Token | Token ID
|:---:|:---:|:---:|:---:|
| `l` | 0 | `lo` | 7 |
| `o` | 1 | `low` | 8 |
| `w` | 2 | `lowe` | 9 |
| `e` | 3 | `lower` | 10 |
| `r` | 4 | `lowes` | 11 |
| `s` | 5 | `lowest` | 12 |
| `t` | 6 | — | — |

### 4.2、合并规则与优先级

合并规则记录“哪两个 Token 可以合成什么”；优先级来自规则在训练中被学到的先后顺序，也叫 **Merge Rank（合并排名）**。

| 优先级（数字越小越优先） | 合并规则 | 训练时该轮出现次数 |
|:---:|:---|:---:|
| 1 | `l` + `o` → `lo` | 3 |
| 2 | `lo` + `w` → `low` | 3 |
| 3 | `low` + `e` → `lowe` | 2 |
| 4 | `lowe` + `r` → `lower` | 1 |
| 5 | `lowe` + `s` → `lowes` | 1 |
| 6 | `lowes` + `t` → `lowest` | 1 |

这里存在频率相同的情况：第一轮的 `l o` 和 `o w` 都出现 3 次；第三轮合并后，`lowe r`、`lowe s`、`s t` 都出现 1 次。本例沿用前文的选择顺序，实际训练需要规定频率相同时如何选择。因此，**语料加上平局处理规则、停止条件，才能确定最终结果**；如果提前停止，词表和规则也会相应减少。

### 4.3、训练与使用

**训练Tokenizer：**

1. 收集大量训练文本；
2. 初始化基础 Token；
3. 统计相邻 Token 对的出现频率；
4. 合并最高频的 Token 对；
5. 重复 3-4，直到达到目标词表规模；
6. 保存词表和合并规则。

**使用 Tokenizer：**

1. 输入一段新文本；
2. 拆成基础 Token，在当前相邻且能匹配规则的 Token 对中，反复优先执行排名靠前的合并，直到没有规则可用；
3. 查询词表，转换为 Token ID；
4. 将 Token ID 交给模型。

例如，使用上面的规则处理 `lowest`：

```text
l o w e s t
→ lo w e s t    （规则 1）
→ low e s t     （规则 2）
→ lowe s t      （规则 3）
→ lowes t       （规则 5）
→ lowest        （规则 6）

最终 Tokens：["lowest"]
最终 IDs：   [12]
```

规则 4 需要相邻的 `lowe` 和 `r`，在这里不适用，所以不会执行。

## 5、BPE 算法的实现优化

前面的步骤便于理解，但如果每轮都“扫描全部语料 → 重新统计 → 找最高频组合 → 再扫描合并”，大量时间会花在重复工作上。实际实现通常保留统计结果，**每次合并后只处理发生变化的部分**。

### 5.1、相同片段只保存一份，用次数作为权重

沿用只在单词内部合并的设定。如果语料中 `low` 出现 1,000 次，不必保存并反复处理 1,000 份相同的字符序列，可以先汇总为：

```text
l o w       × 1000
l o w e r   × 500
l o w e s t × 200
```

统计时乘上权重，例如 `l o` 的总频次为 `1000 + 500 + 200 = 1700`。合并时，每种单词的表示只更新一次，权重保持不变。

这与直接删除重复文本不同：**重复次数仍然参与统计，只是省去了相同序列的重复处理。** 实际系统也可以按相同的预切分片段汇总。

### 5.2、建立索引，只访问包含目标组合的片段

先记录“某个 Token 对出现在哪些片段中”，这种从组合查找位置的结构叫**倒排索引**。

例如，完成前两次合并后：

```text
片段 0：low
片段 1：low e r
片段 2：low e s t

索引：(low, e) → {片段 1, 片段 2}
```

当选中 `low + e → lowe` 时，直接处理片段 1、2，片段 0 无须检查。语料很大、某个组合只出现在少量片段里时，这能省去大量无关扫描。也可以维护更细的出现位置，但需要额外内存和更新开销。

### 5.3、只增减受影响的频次，不重新统计全部组合

以片段 2 的一次合并为例：

```text
合并前：low e s t
合并后：lowe s t
```

它对频次表的影响只有：

| 相邻 Token 对 | 变化 |
|:---|:---|
| `(low, e)` | 减少 1 次 |
| `(e, s)` | 减少 1 次 |
| `(lowe, s)` | 增加 1 次 |
| `(s, t)` | 不变 |

如果这个片段的权重是 200，上述增减量就分别乘以 200。其他片段的变化也累加到同一张频次表中。

一般来说，合并 `A B → AB`，只会改变该位置以及左右邻接关系。实现时还要正确处理重叠，例如 `a a a` 中有两个相邻的 `a a`，但不能让中间的 `a` 同时参与两次合并。索引与局部频次更新可参考原作者的 [subword-nmt 实现](https://github.com/rsennrich/subword-nmt/blob/master/subword_nmt/learn_bpe.py)。

### 5.4、用优先队列快速找出最高频组合

即使频次已经维护好了，每轮遍历整个频次表找最大值，仍然有开销。可以用**最大堆**保存候选组合：频次最高的组合位于堆顶，避免反复全表查找。

若堆中有 $P$ 个条目，读取堆顶是 $O(1)$，弹出或插入通常是 $O(\log P)$；遍历全部候选找最大值则是 $O(P)$。

频次变化后，可以把带有最新频次或版本号的条目放入堆，旧条目暂时保留。弹出时检查它是否仍然有效，过期就跳过，这叫**惰性删除**。堆顶必须经过校验才能用于合并。

这类加速需要用额外内存保存索引和候选记录；它也不意味着整个训练过程都是 $O(\log P)$，访问和修改片段仍然需要时间。词频汇总、索引、堆和失效检查的组合可参考 [Tokenizers 的 BPE 训练实现](https://github.com/huggingface/tokenizers/blob/v0.22.1/tokenizers/src/models/bpe/trainer.rs)。

### 5.5、使用阶段：按排名维护候选，只更新邻居

训练完成后，编码新文本不再统计语料频率，而是遵循保存的 Merge Rank。这里同样可以用优先队列，但应当是**排名靠前者优先的最小堆**。

为避免每合并一次就移动后面的全部元素，可以为每个 Token 记录前后邻居的位置：合并时修改相邻关系，并标记被合并的节点；再将能匹配规则的新相邻对加入堆，其他位置无须重新扫描。

例如，`low e s t → lowe s t` 后，只需检查新组合 `(lowe, s)`，后面的 `(s, t)` 没有变化。这种邻接结构和候选堆的配合可参考 [Tokenizers 的编码合并实现](https://github.com/huggingface/tokenizers/blob/v0.22.1/tokenizers/src/models/bpe/word.rs)。

这些方法主要减少重复计算。若要与基础实现得到相同结果，还必须保持相同的边界设置、频率平局规则和重叠合并顺序；减少训练数据或提前停止则会改变学习结果，应另行评估。

对应的可运行代码见 [BPE 对比实验](../Lab/Tokenizer/README.md)，可训练基础版与优化版、比较耗时，并输入文本查看 Token 和 Token ID。

## 四、Token ID 与 Transformer 的输入处理

Tokenizer 输出的是整数序列，而 Transformer 需要处理向量。因此，Token ID 还需要经过 **Embedding（嵌入层）**。

### 1、Embedding 的作用

假设 Tokenizer 输出：

$$
[40,\ 1842,\ 7621,\ 5913,\ 13]
$$

Embedding 层包含一个可训练的参数矩阵：

$$
E\in\mathbb{R}^{V\times d}
$$

其中：

- $V$：词表大小，例如 50,000。
- $d$：每个 Token 的向量维度，例如 768。

假设 Token ID 为 1842，则取出 Embedding 矩阵中对应的向量：

$$
\mathbf e_{1842}=E[1842]\in\mathbb{R}^{768}
$$

也就是说：**Embedding 并不是直接拿 Token ID 进行数学计算，而是使用 Token ID 查找对应的可训练向量。**

### 2. 输入数据的维度变化

假设输入包含 5 个 Token，每个 Token 的 Embedding 维度为 768。
经过 Embedding 后：

$$
X\in\mathbb{R}^{5\times768}
$$

即原本的 5 个整数，现在变成了 5 个 768 维向量。

| 对比 | 整数序列中的 ID | Embedding 向量 |
|:---:|:---:|:---:|
| 一个 token | 一个整数 | 一组浮点数 |
| 主要作用 | 标识 token、查询词表 | 参与模型计算 |
| 数值关系 | 通常没有语义意义 | 训练后可以反映语言规律 |
| 如何得到 | Tokenizer 查词表 | Embedding 层查可训练的向量表 |

### 3、获取 Embedding
Embedding 层通常是先随机初始化，再随着整个语言模型一起训练得到的。 它不是 Tokenizer 生成的，也不需要人工为每个词编写含义。

从零训练模型时，这些数值通常是随机生成的小数，最开始没有有用的语言含义。它们通过下面的过程逐渐改变：
1. 读取训练文本。 例如输入“我喜欢吃”，目标是预测后面的“苹果”。这里假设这些词各自对应一个 token；
2. 进行预测。 输入 token 的 ID 查出向量，经过 Transformer 等计算，得到下一个 token 的概率分布；
3. 计算误差。 用损失函数衡量预测与真实答案之间的差距；给正确答案的概率越低，通常损失越大；
4. 更新参数。 通过反向传播计算梯度，再由优化器调整 Embedding、Transformer 等参数，使模型更容易预测正确。

## 五、Tokenizer 的文本编码

Tokenizer 有两个重要操作：

- **Encode（编码）**：文本转换为 Token ID。
- **Decode（解码）**：Token ID 转换为文本。

以本文的词表和合并规则为例：

```text
编码："lower" → ["l", "o", "w", "e", "r"]
             → ["lo", "w", "e", "r"]
             → ["low", "e", "r"]
             → ["lowe", "r"]
             → ["lower"] → [10]

解码：[10] → ["lower"] → "lower"
```

编码时先拆成基础 Token，再按已保存的优先级合并，最后查词表得到 ID；解码时反向查词表，再还原文本。**编码的结果是整数序列，后续由模型的 Embedding 层转换为向量。**

## 六、Tokenizer 其它重要概念
### 1、特殊 Token

除了普通文本 Token，Tokenizer 还可能包含特殊 Token。

| 特殊 Token | 作用 |
|---|---|
| BOS | 表示序列开始 |
| EOS | 表示序列结束 |
| PAD | 用于批量处理时填充序列 |
| UNK | 表示未知 Token |

例如：

```text id="kofmcs"
<BOS> Hello world <EOS>
```

这些是示意写法，实际模型使用的特殊 Token 名称和编号可能不同。

### 2、Token 数量与字数区别
例如：

```text id="r07anp"
I love machine learning.
```

可能被分成 5 个 Token，也可能是其他数量。

中文同样如此：

```text id="3s14qr"
我喜欢机器学习
```

根据具体 Tokenizer，可能被切分成：

```text id="ztupp4"
我 | 喜欢 | 机器 | 学习
```

也可能采用完全不同的切分方式。

因此：

$$
\text{Token 数量}\neq\text{字符数量}
$$

### 3、Tokenizer 与上下文长度的关系
LLM 的上下文长度通常以 Token 为单位，而不是以字数为单位。
例如，某模型支持 8,192 个 Token 的上下文长度，并不意味着能够输入 8,192 个汉字。
实际能容纳多少文字，取决于 Tokenizer 的分词结果。

此外，输入提示词、历史对话以及生成内容都可能占用上下文预算。

## 七、Tokenizer 优化

Tokenizer 优化的目标，是在**文本覆盖能力、Token 数量、词表大小、处理速度和模型效果**之间取得平衡。它不只是“尽量把文本合成长 Token”。

首先要区分两种情况：

| 场景 | 可以重点优化什么 |
|:---|:---|
| 从零训练 LLM | 训练语料、分词算法、基础单位、词表规模、预切分和规范化策略 |
| 使用已有的预训练 LLM | 保持与模型匹配的 Tokenizer，优化编码速度、批处理和输入组织；必要时扩展词表并继续训练 |

### 1、优化目标

同一段文本被拆成的 Token 越少，通常意味着可以用更少的序列位置表达这些内容。但 Token 数量只是一个指标，还要考虑词表和模型计算的成本。

以本文的三个单词为例，不计算换行或额外特殊 Token：

| 合并阶段 | 词表大小 | `low` | `lower` | `lowest` | 总 Token 数 |
|:---|:---:|:---|:---|:---|:---:|
| 仅初始字符 | 7 | `l o w` | `l o w e r` | `l o w e s t` | 14 |
| 完成前 3 次合并 | 10 | `low` | `lowe r` | `lowe s t` | 6 |
| 完成全部 6 次合并 | 13 | `low` | `lower` | `lowest` | 3 |

这说明，增加词表可以减少这份语料的 Token 数。但这个结果不能保证在其他文本上也同样有效，需要用未参与 Tokenizer 训练的文本验证。

例如，语料中没有 `high`，初始字符也没有 `h`、`i`、`g`。如果没有额外覆盖或回退机制，这个示例 Tokenizer 就无法完整表示它。

**压缩已见文本的能力，与表示新文本的能力，需要分别检查。**

### 2、优化训练语料

BPE 根据训练语料里的相邻 Token 对频率学习规则，因此语料的组成会直接影响词表。

如果英文占绝大多数，许多词表位置可能分配给英文片段；中文常用表达可能被拆得较碎。同样，主要用普通文章训练的 Tokenizer，不一定适合处理大量程序代码。

优化时主要考虑：

- **覆盖实际任务**：模型要处理中英文、代码、公式还是专业文本，Tokenizer 的训练语料就应包含相应内容。
- **控制各类语料比例**：多语言场景不能只看整体平均值，还要检查每种语言是否被拆得过碎。
- **减少无意义重复和噪声**：重复网页模板、乱码或抓取错误会影响频率统计，占用有限的词表位置。清理时也要保留真实文本应有的频率差异。
- **保留有效格式**：代码中的缩进、换行、标点，以及文本中的空格，都可能携带信息，不能一律删除。
- **覆盖常用领域表达**：高频术语可以考虑合并，但不需要为每个罕见术语都分配完整 Token，子词组合仍然重要。

这里优化的是 **Tokenizer 的训练语料**。Tokenizer 训练完成后，普通输入中多出现几次某个词，并不会自动改变词表或合并排名。

### 3、选择合适的词表大小

词表太小，文本往往被拆得较碎；词表太大，则需要更多参数，而且其中一些 Token 很少出现，可能缺少足够训练。

| 词表规模 | 常见收益 | 需要承担的成本 |
|:---|:---|:---|
| 较小 | Embedding 和输出层规模较小，便于复用基础片段 | 同一文本的 Token 数可能较多 |
| 较大 | 可以收录更多常见长片段，减少序列长度 | 参数和输出预测计算增加，低频 Token 可能训练不足 |

前文的 Embedding 矩阵为：

$$
E\in\mathbb{R}^{V\times d}
$$

因此，输入 Embedding 的参数量为：

$$
N_{\text{embedding}}=Vd
$$

例如，向量维度为 4,096，词表从 32,000 扩大到 64,000，输入 Embedding 就增加了：

$$
(64{,}000-32{,}000)\times4{,}096
=131{,}072{,}000
$$

即约 **1.31 亿个参数**。语言模型的输出层也要对词表中的 Token 进行预测；如果输入 Embedding 与输出层不共享权重，输出层还会增加相应参数。

另一方面，更短的序列通常能减少模型处理这些文本的计算。在标准全注意力中，注意力分数矩阵的大小随序列长度的平方增长，但整个模型的耗时还受其他计算和实现方式影响。

所以，**应比较“词表增大的成本”和“序列缩短的收益”，不能只看哪种方案的 Token 最少。**

### 4、完善字符覆盖与回退机制

真实输入可能包含生僻字、其他语言字符、emoji 或特殊符号。即使语料很多，也很难提前收录所有可能的完整词语。

常见处理方式包括：

| 方式 | 基本做法 | 特点 |
|:---|:---|:---|
| 字符级基础词表 | 先保留一批基础字符，再学习更大片段 | 常用字符容易表示，覆盖范围取决于基础字符集合 |
| Byte-level BPE | 从完整的 256 种字节值开始学习合并 | 可表示编码后的文本字节，不必收录每个 Unicode 字符 |
| Byte fallback（字节回退） | 常规切分无法覆盖某个字符时，退回它的字节表示 | 减少未知字符造成的信息丢失，但可能产生更多 Token |

例如，汉字“中”的 UTF-8 编码由三个字节组成：

```text
中 → E4 B8 AD
```

如果只能使用单字节 Token，它可能需要 3 个 Token；如果已经学到覆盖这些字节的合并，也可能用更少的 Token 表示。

SentencePiece 提供的 `byte_fallback` 就是将未知片段分解为 UTF-8 字节的机制，具体见[其参数定义](https://github.com/google/sentencepiece/blob/master/src/sentencepiece_model.proto)。

**能够表示，不等于表示得高效，也不等于模型已经学会理解。** 某类文字即使能通过字节表示，如果长期被拆得很碎，仍会消耗更多上下文位置；模型理解它也需要相应训练数据。

### 5、优化预切分与规范化

实际 Tokenizer 往往不只是执行 BPE，还会包含其他步骤：

```text
原始文本
→ 规范化（可选）
→ 预切分（可选）
→ BPE 等分词算法与 ID 映射
→ 加入特殊 Token 等后处理（可选）
```

**预切分**先规定哪些片段可以参与后续合并。例如，规定只在单词内部合并，因此不会把 `low` 与下一个单词连接起来。实际系统可以按空白、标点、文字类别或数字等设置边界，边界会限制后续合并范围。具体流程可参考 [Tokenizers 官方文档](https://huggingface.co/docs/tokenizers/main/en/pipeline)。

不同内容需要不同考虑：

- **中文**：没有天然的单词空格，不能只照搬按英文空格分词的思路；可以直接学习字符或字节片段，不必先做中文词语切分。
- **代码**：要保留缩进、换行和运算符，也可以评估常见代码片段的合并收益。
- **数字**：`2026` 可以设计为整体、固定长度片段或单个数字等不同切法。较长片段可能减少 Token，但并不能据此保证算术能力更强。

**规范化**则改变输入文本本身，例如统一部分 Unicode 写法、转换大小写或处理空白。它可能减少重复形式，但也可能丢失信息：

```text
大小写合并：Apple 与 apple 可能失去区别
删除空格：  可能破坏 Python 代码缩进
统一字符：  某些原本不同的字符写法可能无法恢复
```

因此，不能把“文本更整齐”直接当成优化。若目标要求保留原文，应验证编码再解码后能否精确还原；如果设计上允许规范化，则应按明确的规范化结果验证。

### 6、已有预训练模型的词表调整

**Tokenizer 保存“文本 → ID”的映射，模型的 Embedding 保存“ID → 向量”的映射。修改词表，不会自动修改模型参数。** 例如：

```text
原来的输入："lower" → ID 10 → E[10]
更换后输入："apple" → ID 10 → E[10]（模型参数没有变化）
```

模型只收到 `10`，因此仍取出 `E[10]`。这个向量及后续网络已经适应了 `lower` 的用法，无法仅凭新词表就改为表示 `apple`。输出时也会错位：原本应解码为 `lower` 的 `10`，会被新词表还原成 `apple`。

增加领域 Token 时，通常应**保留旧 ID，为新 Token 追加 ID，同步扩展输入 Embedding 和输出层，再继续训练并评估效果**。仅把术语加入词表，不会让模型自动学会它的用法；没有继续训练的条件时，应保留原配 Tokenizer。词表扩展的具体操作见 [Transformers 文档](https://huggingface.co/docs/transformers/main/en/main_classes/tokenizer)。

### 7、优化编码与批处理速度

假设要处理 1 万条文本，优化重点是减少加载、调用和重复编码的开销，**文本切成哪些 Token 可以保持不变**。
- 高效实现：使用成熟的高性能编码器，避免自己用脚本逐字符扫描和合并；确认编码结果一致；
- 批量编码：每次传入一批文本，例如 100 条，减少逐条调用的开销；合适的批量大小需要实测；
- 复用实例：程序开始时加载一次 Tokenizer，后续反复使用，避免每条文本都重新读词表。
- 提前编码：固定训练集只编码一次，把 ID 序列保存下来，后续多轮训练直接读取；Tokenizer 或配置改变后应重新编码。

**按长度组批则能减少后续模型计算中的 Padding 浪费。** 在常见的批处理方式中，同一批序列需要补齐到相同长度，短序列会添加 PAD。

例如，4 条文本编码后的长度为 `10、12、100、102`，每批放 2 条，并补齐到该批最长序列：

| 分组方式 | 补齐后的长度 | 新增 PAD 总数 |
|:---|:---|:---:|
| 长短混放：`(10, 100)`、`(12, 102)` | `(100, 100)`、`(102, 102)` | 90 + 90 = **180** |
| 长度接近：`(10, 12)`、`(100, 102)` | `(12, 12)`、`(102, 102)` | 2 + 2 = **4** |

有效 Token 都是 224 个，但第二种分组少填充了 176 个位置，通常能减少模型的无效计算。

验证速度时，直接比较**同一份文本在相同环境下的总处理时间**，并区分 Tokenizer 编码耗时和后续模型耗时。高效编码与批量处理的实现可参考 [Transformers 文档](https://huggingface.co/docs/transformers/main/en/main_classes/tokenizer)。

### 8、评估优化有效性

选一份未参与 Tokenizer 训练、包含实际任务常见内容的文本，优化前后都用它测试，主要看三点：

1. **有没有丢信息**：把文本编码再解码，与原文对比，检查生僻字、空格、换行等是否保留。如果设置了规范化，则与预期的规范化文本对比。
2. **有没有节省资源**：例如，同一份文本从 6,000 个 Token 变为 4,000 个，说明序列更短；但词表可能也变大，因此还要在相同硬件和批量设置下，比较编码耗时、配套模型的运行时间和显存占用。
3. **模型效果有没有下降**：用相同任务测试与各自 Tokenizer 配套训练或适配后的模型，例如代码任务比较生成代码通过测试的比例。若 Token 更少但错误更多，就需要权衡这项优化是否值得采用。
